## Scope and critical truth distinctions

The actual `src/ai_osop/api/main.py:register_optional_mcp_servers` names eleven slots. The shared `MCPRegistry` and `MCPConnection` then perform transport health, typed MCP initialization, negotiated tool schema, exact tool authorization, budget reservation, audited HTTP dispatch and receipt processing. In production, the **separate** `FlowMCPActionExecutor` consumes an original durable 0027 Action against a current signed Flow, executing Task and dispatched Subtask, current signed ROE and distinct persisted human approval, then marks a one-shot attempt `UNKNOWN` **before** MCP transport. Native Go `authority_status` additionally requires genuine independently issued 0029 one-use grant and resource-specific 0033 supervisor authority. The receipt is provider testimony; independently observed physical target effects must be proven elsewhere.

**What the new runtime test actually does:** each one of the eleven genuine central registry/client paths connects to **one newly owned disposable listener** on `127.0.0.1:<OS-assigned-port>`; listeners are used sequentially within the same Python test process. The local **test** server advertises a clearly labelled synthetic but valid typed `list_tools` (inert, unapproved `READ_ONLY`) and a nonexecuting, fake consequential `scan_target` tool (`RECON_ACTIVE`, `requires_approval=True`, exact primitive target schema). It is not an installed instance of the named server. No port 8081–8098 or real configured listener is probed.

For **every** named slot, the test executes and checks this sequence:

1. **Actual transport/manifest:** real `MCPRegistry.register_server` reaches loopback `/health`, and actual `initialize_server` parses the fixture's valid `ready` tool definitions. This proves the client path negotiates a typed fixture; it **does not prove** the real named provider is ready.
2. **Actual original Action tool schema:** `_tool_definition` admits only inert `list_tools` as a scope-checked `READ_ONLY` declaration; `_bounded_params` admits only exact empty parameters; `_manifest_sha256` binds the negotiated schema. It rejects the fake `scan_target` consequential name even though the remote fixture advertises `RECON_ACTIVE` with an apparent human-approval flag. `requires_approval` metadata cannot manufacture operator approval.
3. **Actual direct Task/ROE admission denial:** `MCPRegistry.execute_tool` attempts the fake target-bearing scan with an `eng-...`/`task-...`/`flow-...` context lacking signed source authority. Real `check_tool_authorization` fails closed (`scope_unavailable` or current equivalent) **before** charging budget, emitting durable acceptance or sending HTTP. The `.invalid` URL is never contacted.
4. **Actual budget denial:** an explicitly labelled test-only quota callback rejects inert `list_tools` in a nonbootstrap engagement. The real registry returns `quota_exceeded`; the remote fixture receives **zero** `/mcp/execute` requests. This callback proves local gating on a negative result; it is **not** a genuine Redis atomic reservation or signed budget admission.
5. **Actual original 0027 dispatch denial:** constructing `FlowMCPActionExecutor` without `SessionMemory` fails. A real `SessionMemory`-typed object with isolated **read-only stubs returning `None`** exercises the actual executor's `_authority` at dispatch; without a signed Flow/ROE/Task, `dispatch` fails **before consulting the store or sending provider I/O**. No fake signed approvals, fake complete `Task`, fake PG Action row, or patched successful authorization is used. This is a negative verification, **not** a successful original Action execution.
6. **Only benign provider dispatch:** with the runtime's explicitly documented `api-bootstrap` exception for harmless discovery, the real registry sends exactly one `list_tools` request to the local fixture, receives HTTP 200, and reports `status=success` **as untrusted provider testimony only**. The actual result sanitizer strips `target_effect_verified`, nested `production_certified`, `signed_provider_receipt` and other forged authority labels, retains only ordinary fixture tool counts, and explicitly sets provenance `target_effect_verified=False`. The claimed fake receipt is not promoted to `metadata.signed_provider_receipt` because it lacks an enrolled Ed25519 attestation. No target-side operation is performed; bootstrap does **not** authorize signed Flow Actions or scans.
7. **Actual one-shot timeout/ACK-loss distinction:** a second inert fixture dispatch receives a server-side HTTP 503 containing a malicious `success` body. The real MCP client reports `UNKNOWN` rather than success or terminal failure; repeating either completed request ID returns `duplicate_request` without resending. This proves in-process original-request dedupe and conservative transport handling, **not** cross-replica durable one-shot execution.
8. **Actual cancel/status authority checks:** absent persisted Task authority, both normal `request_cancellation` and `reconcile_execution` return `denied` before sending network controls. Separately a structurally plausible **untrusted** post-restart claim with no authoritative Task is refused by the real `reconcile_persisted_status` and `cancel_persisted_execution` authorization check; even query-only status cannot be sent just because a caller knows a request ID. There is **no signed stop or independently confirmed physical cancellation**. A lost ACK remains UNKNOWN.

Every fixture contains a defensive `/mcp/execute` guard that would return HTTP 503 for anything other than the exact empty-parameter inert discovery call. Instrumented fixture call lists prove `health`, `initialize`, `execute(list_tools)`, `execute(list_tools)` and **zero consequential `execute`, zero `/mcp/cancel`, zero `/mcp/request/status`**. This intentionally tests denial rather than fabricating signed permission to perform an unapproved status or stop.
