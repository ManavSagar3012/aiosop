# SourceMap native-grant blocker and minimal migration design

**Research snapshot:** 2026-10-21, the original shared working tree at `/burp_mcp/ai-osop`. This is a proposal and qualification record; **no migration, grant issuer, production route, Docker environment, database, or target was changed or executed.** Companion contract tests: `tests/qualification/test_sourcemap_native_grant_blocker_20261021.py`.

## Finding

**An existing 0029 native grant cannot authorize `source-map-mcp/inspect_local_original_sourcemap`, even when all original 0027/0035 approvals exist.** The incompatibility is enforced by the database, central claim validator, original-action source validator, executor issuer branch, and the 0033 worker-supervision store. The 0035 original-source preflight is a *different* one-use credential, not a native 0029 grant or proof of a running container. SourceMap inspection may be authorized through its distinct 0035 path, but that does **not** establish a real 0029/0033 SourceMap worker lifecycle.

The literal 0029 database CHECK does **not** itself constrain `server_id`; in isolation, it admits a row with `server_id='source-map-mcp', tool_name='authority_status'`. The Python issuer/original validator and executor deny that composition. A safe extension must enforce a **paired server and tool allowlist in the database as well**, rather than broadening by tool name alone or using a parenthesization bug such as `tool_name='authority_status' OR tool_name='inspect_local_original_sourcemap' AND side_effect_class='READ_ONLY'`.

## Related mismatches beyond the CHECK

1. **Grant declaration and digest semantics differ.** The existing 0029 `_validate_claims` binds `parameters_sha256 == SHA256('{}')` and `manifest_sha256 == _native_manifest_sha256(server_id)`, based on the inert builtin. Original SourceMap requires exactly `{artifact_sha256}`, its signed registry declaration/parameters SHA, and a **different** 0013/0015 reviewed Flow metadata manifest. Do not substitute its `artifact_sha256` for `resource_sha256`, the declaration digest, or the metadata manifest.
2. **Current generic resource verification has a different manifest format.** `NativeMCPExecutionGrantStore._resources` rebuilds a `flow_resource_exports.make_manifest` and checks `tasks.payload.mcp_resource_sha256`, whereas `SourceMapSourceAuthorityStore._source` verifies the SourceMap-specific Task `resource_artifact_id`, `resource_artifact_sha256`, `resource_manifest_sha256`, `resource_command_sha256`, independently recomputed `_metadata_manifest`, byte SHA and senior review. In addition, `approved_folder_stage_plan` expects the former manifest's `items`, while `SourceMapSourceAuthorityStore._original_manifest` returns an SHA and artifact ID. A SourceMap path must explicitly reconcile these **different formats and Task authorities**, not equate or silently translate their hashes.
3. **0033 depends on a verifiable grant and is currently the Go lifecycle.** `NativeMCPWorkerSupervisionStore.record` calls the shared `_verify(token)` and `self.grants._source(...)`. Its latest immutable event stores `claims_sha256` and `signature_sha256`, **not the signed observation bytes**. The actual signed running observation has `expected_revision = prior revision`, followed by durable CAS `row.revision = prior + 1`; a correct current-DB witness must check this one-step relation and the signed event hash. A ledger entry alone does not show a live PID/container or mounted filesystem.
4. **SourceMap staging is separately host-owned.** `sourcemap_original_readonly_provisioner.py` explicitly states that native 0030/0031 offer hashes are not SourceMap staging authority. `sourcemap_supervisor_source_issuer.py`, `sourcemap_supervisor_current_db_witness.py`, `sourcemap_native_mount_observer.py` and `sourcemap_original_host_coordinator.py` have their own independently enrolled process, current DB and mount-signature requirements. These components must agree on one actual live original Action/lease/epoch and must not obtain authority from test-signed proofs.
5. **Preflight orchestration needs one owner.** The host coordinator currently reserves and issues the sole 0035 preflight after receiving a signed supervisor source; the source issuer itself requires fresh signed 0035 status, and the status issuer requires that preflight to exist. This is a dependency cycle for first-time staging. At least one coordinated **non-consumptive bootstrap** using an independently verified real supervisor must precede exactly one 0035 issuance. Merely rearranging calls or reissuing 0035 would violate its uniqueness contract.

## Minimal production extension after prime coordination

This is a staged change proposal, **not** an instruction to activate SourceMap automatically. Select a new Alembic revision after checking the **live current head** (the inspected files form the `0035` chain; concurrent developers may have already allocated the next number). Do not rewrite historical migration `0029`, `0033` or `0035`.

### A. Add one strictly paired capability to the grant schema

Use an additive migration such as `migrations/versions/<next_free_revision>_sourcemap_native_grant_pair.py`, with `down_revision` resolved only after coordination. In that migration, replace `ck_native_mcp_grant_inert_tool` with a **fully parenthesized finite mapping** and retain all unrelated existing constraints and foreign keys:

```sql
CHECK (
  side_effect_class = 'READ_ONLY'
  AND (
    (server_id IN ('recon-mcp', 'payload-mcp', 'nuclei-mcp',
                   'shodan-mcp', 'threat-intel-mcp', 'security-bridge')
     AND tool_name = 'authority_status')
    OR
    (server_id = 'source-map-mcp'
     AND tool_name = 'inspect_local_original_sourcemap')
  )
)
```

Ensure the migration checks that no legacy rows violate the new pairing before replacing the old CHECK. Keep `action_id` and `request_id` unique, grant event history immutable, grant TTL/revision/signed-hash checks and `0033.grant_id` FK unchanged. Preserve the six current Go service flows. The database permits only *representing* a SourceMap grant; it does not establish a valid SourceMap issuance/redeem path.

Coordinate edits to **all** of the following, with one owner per file:

The likely **minimum coherent release** therefore includes the new migration, source-specific grant claim/issuer/redemption branch, one trusted supervisor-to-host transport, independently current host witness, deterministic reviewed SourceMap artifact offer, one 0035 issuance coordinator, and lifecycle tests. A CHECK-only change or an optimistic feature flag does not meet this release boundary.

### C. Required failure and replay qualification before enabling

1. On disposable PostgreSQL with the **new migration**, prove literal CHECK rejects unrelated server/tool pairs, unknown side-effect classes, malformed grant IDs and null/misbound identities. Verify existing Go paired grants remain admitted and SourceMap is impossible without a separately reviewed, signed original Task and correctly enrolled service.
2. Assert two simultaneous grant issuances for the same committed 0027 Action/request have **exactly one** winner. The loser must receive UNKNOWN/409 and must not reach a handler. Repeat for two redemptions, 0030 offers, first 0035 source preflight, and host stage one-shot. Lock order stays 0027 Action → 0029 grant → 0030 offer → 0032 stage receipt → 0033 observation, with no reverse lock path.
3. Revoke owner/reviewer, signed ROE, Task, source SHA, 0026 catalog, lease or issuer enrollment between issue and redeem, and between redeem and status. Every revoked/stale branch must deny with **no** original byte re-read, additional grant, automatic retries or 0027 UNKNOWN-to-prepared transition.
4. Crash after `0027 mark_dispatched`, after 0029 issue, after 0029 redeem, after 0035 commit, after host journal fsync and after 0030 offer commit. On restart, use read-only status/reconciliation, never call `inspect_local_original_sourcemap` again for the same Action. Lost ACK is UNKNOWN, not success.
5. Independently verify the reviewer-approved **original** 0013 BYTEA SHA, artifact ID and size, exact Task's command SHA and manifest, separate trusted signing roots, 0033 epoch/CAS event signature/digest, live PID/process identity and mount namespace/read-only source. Negative cases: swapped tenant/owner/Task/reviewer, forged/grandfathered observation, mismatched original SHA, old epoch, changed folder, stale lease, untrusted signature, missing supervisor, missing issuer bearer, corrupted journal.
6. Test benign local original files only. Distinguish provider-signed processing receipt from independently verified target effects. Do not contact public targets, claim remote execution, or label fake-PG/static/simulated tests as production qualification.

## Qualification delivered with this document

`tests/qualification/test_sourcemap_native_grant_blocker_20261021.py` loads the **actual** Alembic constraint AST, evaluates its SQL `CHECK` predicate in isolated in-memory SQLite, and asserts SourceMap fails while the current inert builtin shape succeeds. It also probes actual Python `_validate_claims`, traces the original Action and executor issuer restrictions, checks 0030/0031/0033/0035 one-use, immutable and signed-source requirements, and exercises a proposed **pairwise** SQL truth table to prevent accidentally granting all READ_ONLY tools. All demonstrated future acceptances are **proposed policy test vectors**, not present production permissions.

**Scope and evidence limit:** These are code and SQL-expression tests, not PostgreSQL execution, TLS attestation, real Docker supervision, native worker lifecycle or end-to-end SourceMap verification. Current production must continue denying a 0029 SourceMap grant until the complete, separately reviewed extension is implemented and tested.
