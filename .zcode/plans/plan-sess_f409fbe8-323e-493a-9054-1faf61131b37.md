## Architecture: What changes

### 1. The ReasoningLoop (Priority 1 — the core change)

Replace the phase-monitor's "check completion → advance phase → hardcode tasks" loop with a **continuous reasoning loop** that runs alongside the existing phase monitor:

```
while engagement_active:
    1. Observe: read the current graph state (findings, endpoints, hypotheses, assets)
    2. Generate hypotheses: call HypothesisEngine (already exists, already writes to graph)
    3. Select highest-value hypothesis: rank by confidence × value_engine score × novelty
    4. Dispatch: create a Task for the hypothesis's recommended_test against its target_id
    5. Wait for the task to complete (or timeout)
    6. Evaluate: did the finding confirm/refute the hypothesis? Update hypothesis status.
    7. Learn: if confirmed, record to FindingsKnowledge (already auto-records)
    8. Loop: generate NEW hypotheses based on what was just learned
```

**New file**: `src/ai_osop/orchestrator/reasoning_loop.py`
- `class ReasoningLoop` — runs as a background asyncio task alongside `_phase_monitor`
- Constructor takes `orchestrator` (for graph_memory, session_memory, task_scheduler, coordination_bus)
- `async def run(self)` — the main loop above
- `async def _observe(self, eid) -> Dict` — query graph for current state
- `async def _select_hypothesis(self, eid, hypotheses) -> Optional[Hypothesis]` — rank + pick
- `async def _dispatch_hypothesis(self, eid, hyp) -> Task` — create + schedule a Task
- `async def _evaluate_result(self, eid, hyp, task_result) -> None` — update hypothesis status

### 2. Event-Driven Finding Publication (Priority 4)

Wire `GraphMemory.add_vulnerability` to publish a `finding.recorded` event on the coordination bus:

**Edit**: `src/ai_osop/memory/graph_memory.py` — `add_vulnerability` method
- After persisting, publish `finding.recorded` with `{finding_id, vuln_type, endpoint, severity, validated}` on the bus
- The `ReasoningLoop` subscribes to `finding.recorded` — every new finding immediately triggers hypothesis re-generation (adaptive chains, Priority 6)

**Edit**: `src/ai_osop/orchestrator/coordination_bus.py` — add `finding.recorded`, `finding.confirmed`, `hypothesis.generated`, `hypothesis.tested` as documented topic names

### 3. Dead-End Recovery (Priority 3)

When a hypothesis test returns 0 findings (dead end), the reasoning loop generates follow-up hypotheses:

**Edit**: `src/ai_osop/orchestrator/reasoning_loop.py` — `_evaluate_result` method
- If `task_result.findings_count == 0`:
  - Mark hypothesis `status="refuted"`
  - Generate follow-up hypotheses: "was the endpoint authenticated?", "was the parameter JSON?", "should we try a different technique?"
  - These are LLM-augmented: call `think()` with the failure context + prior findings from `FindingsKnowledge`
- If `task_result.findings_count > 0`:
  - Mark hypothesis `status="confirmed"`
  - Generate chain hypotheses: "SSRF found → try metadata?", "IDOR found → try admin objects?"

### 4. Dynamic Planner (Priority 2)

The reasoning loop DOES NOT replace the phase monitor — it runs **alongside** it. The phase monitor still handles phase transitions and the existing deterministic scan path. The reasoning loop adds **adaptive** work on top:

- Phase monitor: schedules the baseline recon + discovery + nuclei (unchanged)
- Reasoning loop: observes what was discovered, generates hypotheses, dispatches targeted tests that the phase monitor would never schedule (e.g. "this endpoint has `?redirect=` — test open redirect → if confirmed, chain to OAuth token theft")

The `ContextManagerAgent` is finally called: the reasoning loop dispatches `generate_hypotheses` tasks to it after each phase entry, so the existing agent + HypothesisEngine get exercised in the autonomous loop for the first time.

### 5. Memory-Driven Planning (Priority 5)

**Edit**: `src/ai_osop/orchestrator/reasoning_loop.py` — `_select_hypothesis` method
- Before selecting, call `BaseAgent.recall_prior_findings` equivalent (query `FindingsKnowledge`) for the hypothesis's target + category
- If prior findings exist for this target type with high success rate → boost confidence
- If prior findings show this technique failed on similar targets → lower confidence, skip

### 6. What stays unchanged

- The phase monitor, task scheduler, and orchestrator main loop keep working as-is
- The deterministic scan path (`bootstrap_discovery` + `run_generalized_scan`) keeps working
- The governed egress, scope enforcement, rate limiting — all unchanged
- All existing detectors, oracles, and agents — unchanged
- The 17 handler modules from the monolith split — unchanged
- Tests + benchmarks — unchanged (new tests added for the reasoning loop)

## Implementation order

2. **Wire it into the orchestrator** — start it alongside `_phase_monitor` in `orchestrator.py`
3. **Event publication** — `graph_memory.add_vulnerability` publishes `finding.recorded`
4. **Dead-end recovery** — `_evaluate_result` generates follow-up hypotheses on failure
